# Vista Arquitectónica de la Funcionalidad

Estilo arquitectónico: **microservicios**. Un frontend web consume APIs REST a través de un API Gateway. Cada microservicio es desplegable en forma independiente y persiste con Database per Service. No se utiliza un monolito Layered.

## Requerimientos no funcionales

| Nro. | Nombre | Descripción | Sign. arq. | Justificación |
| :---: | :--- | :--- | :---: | :--- |
| 1 | Tecnología web | El sistema será desarrollado completamente con tecnología Web. | SI | El lenguaje de programación debe soportar el desarrollo de un frontend web y de APIs REST. El cliente web se comunica exclusivamente con un API Gateway, que enruta hacia los microservicios. Cada capacidad de negocio vive en un microservicio; no se aplica un monolito Layered ni un C/S N-Tier como estilo de la solución. |
| 2 | Alta disponibilidad | A los fines de asegurar alta disponibilidad (7x24x365) se requiere la utilización de bases de datos espejadas (Database Mirroring). | SI | Los microservicios se despliegan en forma independiente (un fallo en uno no detiene al resto). Cada servicio tiene su propia base (Database per Service). El mirroring exige dos instancias Amazon distintas por base crítica, de modo que ante la caída de una la réplica continúe el servicio. |
| 3 | Despliegue espejado de la base de datos en la nube | La base de datos debe alojarse en servidores Amazon en la nube. | SI | Los microservicios y sus bases se despliegan en AWS. Las bases espejadas viven en nodos de datos separados; los servicios de aplicación pueden agruparse con el patrón Multiple Service per Host. El API Gateway mantiene transparente para el usuario el uso de bases en la nube. Complementa el RNF 1 Tecnología web y el RNF 2 Alta disponibilidad. |
| 4 | Seguridad de usuarios | El sistema debe preservar la seguridad de los datos de los usuarios y sus transacciones, permitiendo la administración de usuarios y permisos. | SI | Se resuelve con el microservicio de Usuario: autenticación, autorización y sesión web con caducidad por inactividad, de modo que la sesión no sea accesible más que por el usuario que la generó. El Gateway exige un token emitido por este servicio antes de enrutar al resto. |
| 5 | Envío de notificaciones por mail | Se debe notificar vía email al momento de recibir un bolsín a la CM origen, y al momento de consultar la ubicación de bolsines, detallando la documentación enviada en cada bolsín. | SI | Microservicio de Notificaciones con un Adapter/Broker hacia la API de Outlook de Microsoft Graph. Encapsula la transformación entre el modelo de la aplicación y Graph, sin acoplar el resto de los servicios al proveedor de correo. |
| 6 | Dispositivo GPS Tracker | Cada bolsín debe contar con un dispositivo GPS Tracker que permite al Encargado de Bolsines de cada CM realizar el seguimiento de los bolsines. | SI | El microservicio de Seguimiento expone un contrato único de localización. Un patrón Adapter unifica los tres modelos (XTR-4500L, NavTrack QX-7A y GeoPulse MTR-900), cuyos endpoints, parámetros y formatos de respuesta son distintos. |
| 7 | Visualización de bolsines en el mapa | El sistema permite al Encargado de Bolsines visualizar en un mapa la ubicación de los bolsines que envía. | SI | Adapter hacia la API de Google Maps en el microservicio de Seguimiento. El mapa se arma con las coordenadas obtenidas vía el Adapter GPS (RNF 6). La integración no vive en el frontend como librería aislada: el servicio orquesta GPS y Maps. |
| 8 | Generación de reportes y estadísticas | Para la generación de reportes y estadísticas el sistema utilizará la herramienta Power BI. | SI | Microservicio de Reportes con Adapter hacia Power BI. No se resuelve importando una librería de exportación de archivos; implica un actor de software externo y un servicio de integración propio (Database per Service o dataset publicado hacia Power BI). |

## Justificación de los casos de uso incluidos en la vista

Los casos de uso del diagrama son representativos de las decisiones arquitectónicas. No se incluye el listado completo del ERS. El ERS no define un proceso automático tipo batch o scheduler; no se inventa un caso de uso de ese tipo.

| Casos de uso | Justificación |
| :--- | :--- |
| 5. Iniciar sesión | Resuelve autenticación, autorización y sesión web. Define el microservicio de Usuario y el contrato que el API Gateway usa para habilitar el resto de las operaciones. (RNF 4 Seguridad de usuarios). |
| 19. Generar Bolsín<br>20. Modificar Bolsín<br>21. Eliminar Bolsín<br>22. Consultar Bolsín | ABMC más complejo: remitos, documentación, número secuencial y estados. Define el microservicio de Bolsines, su API REST, el acceso a *su* base (Database per Service) y la consistencia del agregado bolsín/remito/documentación. El diseño debe sostener despliegue en Amazon y mirroring. (RNF 1 Tecnología web, RNF 2 Alta disponibilidad, RNF 3 Despliegue espejado de la base de datos en la nube). |
| 28. Registrar recepción de bolsín | Transacción de negocio más compleja: actualiza bolsín, remitos y documentación según cuatro situaciones de recepción. Queda en el mismo microservicio de Bolsines para no partir el agregado. Al confirmar, invoca al microservicio de Notificaciones. |
| 29. Notificar recepción de bolsín | Resuelve el RNF 5: interfaz con Microsoft Graph desde el microservicio de Notificaciones. Es el CU representativo de esa interoperabilidad (el CU 30 no se incluye: misma interfaz de correo). Se incluye desde el CU 28. |
| 36. Consultar seguimiento de bolsines | Resuelve el RNF 6 y el RNF 7 en el microservicio de Seguimiento: Adapter GPS (tres modelos), Adapter Google Maps y consulta al microservicio de Bolsines de los bolsines en estado enviado. |
| 37. Generar reporte de bolsines en tránsito<br>38. Generar estadística de movimiento de bolsines | Resuelven el RNF 8 en el microservicio de Reportes: Adapter Power BI, consultas y organización de la interfaz web de informes. |
